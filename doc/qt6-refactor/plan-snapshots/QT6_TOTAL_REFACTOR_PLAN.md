## Commit construction and least-disruptive migration

Use a small replacement seam in the existing owner, not a second competing implementation. A feature has exactly one authoritative writer throughout migration. A compatibility facade may forward commands and publish the new owner's snapshots; it may not maintain another set of business flags or write the backend itself. Read-only comparison against old behavior is allowed in tests; never execute a write twice to compare implementations.

For each work order:

1. Inspect its assigned scopes, original evidence/corrections and current code. Identify the precise requirement and its failure oracle. Discover relevant existing tests before inventing new fixtures.
2. In a disposable worktree, reproduce the baseline defect with the intended regression. Record why it fails. Commit the repair and regression together so the landed parent remains green. A non-reproduced claim needs investigation or documented disposition, not a fabricated failing test.
3. If needed, land a small preparatory extraction that preserves behavior and includes characterization tests. Its first real consumer and tests must land with any new abstraction; avoid unused framework-only changes.
4. Introduce one domain owner or protocol behind the existing facade. Move validation, state reduction and effect orchestration together with their unit tests. Preserve stable entry points until their consumers migrate.
5. Switch one page/action family to typed properties and commands. Add binding/component and real integration coverage for that consumer in the same commit. Do not require a later commit to repair a temporarily broken flow.
6. Remove that old code path only after all its callers and tests are migrated. Preserve compatibility for remaining callers through delegation. Separate unrelated formatting/renames from semantic fixes.
7. Update scope evidence and run the gates below on the exact head. Recheck branch and revision after lint. Report blockers honestly; a blocked validation gate is not a green commit.
8. Update applicable upstream improvement notes. If a required fix needs a Core subtree change, notify the user with the evidence and hold that fix and its dependent work until the user provides input, as required above.

A work order is a scheduling unit, not a mandatory single commit. Split large orders—for example backend admission, authorization, candidate submission and conditional persistence—into independently reviewable commits. Never combine unrelated findings merely because they share a file. Conversely, one common-cause repair can cover multiple scopes when each trigger and acceptance assertion is retained.

Do not remove existing test assertions to make a new design pass. For an invalid or obsolete test, record its original selector/assertion, the requirement it attempted to protect, evidence that its assumption is wrong, replacement protection and the reason for the change. Tests that access removed internals should migrate to equivalent public behavior. A known baseline failure is not automatically an invalid test; fix valid failures before final acceptance. Keep unexplained failures open.

Persisted wallet/request/settings formats and compatibility are separate contracts. Avoid format changes during owner extraction. Where unavoidable, use a dedicated migration commit with old/new data fixtures, interruption/recovery tests and the retained Qt Widgets/old-binary compatibility journeys. Do not silently change product decisions for held findings.

## Finding-level acceptance contract

Each of the 329 scopes must have all of the following, or an explicit non-defect disposition with supporting evidence:

- The original trigger, exact data/preconditions and a behavioral oracle independent of the new implementation.
- Baseline app/Core revisions and a failing test result attributable to that cause. If already fixed, identify the covering revision/code and a passing protective regression; do not call it newly fixed.
- A precise fix commit and actual executable unit/component/integration/process selectors, including data-row IDs where relevant. Planning case IDs are not selectors.
- A passing after-result on the actual fix head, and on the final combined series. Assert persisted/backend effects when relevant, not just `phase == Succeeded`.
- Relevant deterministic ordering schedules, failure/rejection cases, and no unintended extra effects.
- Artifact paths, selected/executed test counts and coverage evidence. Empty test selection never passes.

For repeats, link the canonical fix and test, retaining distinct entry points as separate data rows/tests. For held, refuted or expected behavior, preserve evidence and valid behavior protection; do not add a meaningless regression asserting an invented defect. Findings 95, 98 and 253 require the recorded premise checks. Findings 39 and 255 need PR 1090 overlap verification. Split scopes in 55, 99, 100, 208 and 307 remain independent obligations.
