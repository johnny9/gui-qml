## Placement and ownership

The adapter is application code using public wallet methods. It does not alter Core's implementation of the interface, inherit/mirror every wallet method or introduce a second universal wallet FSM. Keep UI workflows, drafts, interest and feature decisions in their existing/planned domain owners. Reuse R01/R08 execution, ownership and task/outcome accounting instead of adding another authoritative ledger.

| Part | Owns | Boundary |
| --- | --- | --- |
| Wallet opening context | Private opening identity, local admission/closing, retained interface/handlers, borrower and drain ownership | Background lifecycle and existing R08 resources; wallet names are not opening identities |
| Narrow effect adapter | Translate feature requests into existing public wallet calls and return owned values/results | Real worker execution; no testing `wallet()`/`context()` accessors, raw `CWallet`, internal mutex/field or direct implementation-service bypass |
| Feature domain owners | Guards, local revisions, prompts, accepted intents, feature outcomes and reconciliation | Serial background mailboxes; pure/testable decisions with injected ports and clocks |
| GUI projections and QML | Cached typed properties/roles, change notifications and narrow user-intent commands | Bounded presentation and necessary native UI handoffs; no Core queries, I/O or domain decisions in getters/handlers |

Public Core value types exposed by the wallet interface remain allowed in the effect adapter. Domain reducers keep their existing Core-independent value boundaries. Production services are injected at composition time; no global service locator or one thread per model. Native dialogs/clipboard handoffs remain narrow presentation adapters with captured intent and retained outcomes.

## What our state will guarantee

| App responsibility | Planned protocol and observable result | Limit to preserve |
| --- | --- | --- |
| Opening lifetime | Local Open -> Closing -> Draining -> Closed; fence app admission on its own close intent or observed unload ingress, retire prompts/views and release the wallet after admitted work/callbacks/borrowers drain | Local Closing is not an earlier authoritative Core Closing state. Do not promise that no operation can enter during Core's pre-notification unload interval |
| Local command ordering | Resource-keyed serial admission and exact opening/operation/review identities; reject stale or duplicate commands and old-result retargeting | Local sequence numbers do not version or serialize independent RPC/Core-timer mutations |
| Local authorization ownership | Track action-bound app authorization interest, overlapping app operations and cleanup ownership; revoke stale prompts and queued protected actions | This does not supply a Core authorization lease or make unconditional global relocking safe against a later RPC unlock. Preserve this open gap explicitly; do not leave the wallet permanently unlocked or weaken security as a workaround |
| Read/publish | Background reads, explicit freshness/unknown/error, pending refresh preservation and atomic GUI publication of owned values | An immutable GUI snapshot is not proof of an atomic backend multi-call snapshot. Prefer existing declared read groups such as `tryGetBalances` and `getWalletTxDetails` |
| Persistent editors | Base value plus local draft/successor revisions; preserve edits across asynchronous saves, notices and view changes; reconcile through existing public observations | Read/compare/write through separate methods cannot guarantee no overwrite of a concurrent RPC writer. Reconciliation is not compare-and-swap |
| Transaction outcome ownership | Retain exact approved terms/transaction identity and admitted effects; represent recording, observed mempool/confirmation state, known failure and uncertainty separately | A void commit return does not prove network acceptance. Absence from the mempool does not alone prove rejection or provide the original reason; observations may change with replacement/reorg |

Only the backend facts provided by the actual interface can authorize backend claims. App state may invalidate its own intent promptly, but cannot make unrelated RPC calls consult its local revision. Shared Core atomicity, authoritative conditional release and earlier backend admission remain separately tracked contracts.

## Command, cancellation and close rules

1. Capture immutable user intent and the original opening/review association. GUI enqueue acceptance is distinct from effect admission and eventual result.
2. Reject closed/stale/duplicate local work before dispatch. Use narrow typed unavailable/error results when a required contract is absent; do not invent backend authority from an app flag. Preserve existing feature behavior during migration rather than silently disabling it.
3. Dispatch Core and blocking I/O through the injected background executor and existing keyed budgets. Preserve reserved control/cleanup capacity and bounded/coalesced replaceable observations.
4. Cancel only work that has not crossed its safe effect boundary. A running or completed mutation remains owned even if the view disappears or the user cancels presentation. Retain/account its actual result before drain.
5. Consume outcomes on the domain owner, check original identity/dependencies and publish cached values on GUI. Stale presentation suppresses publication without losing mutation accounting.
6. On close, fence local admission at ingress, retain admitted tasks and callback/handle leases, finish or transfer cleanup/outcome ownership and release the final backend resource off GUI. Observe physical worker drain; never synchronously wait on GUI.
7. Deduplication is scoped to the in-process owner/ledger. After an uncertain effect or restart, query authoritative state where possible; do not automatically replay writes, signing or broadcast. Do not persist transient tokens, authorization or secrets as a recovery journal.
